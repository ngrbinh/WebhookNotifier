# Transaction and State Consistency

## Scope

This system does not use global distributed transactions (such as 2PC, 3PC, or Sagas) across PostgreSQL, RabbitMQ, and external partner endpoints. Instead, it achieves durable, **at-least-once delivery** using local database transactions, composite idempotency keys, short-lived leases, and explicit retry policies.

This document describes the state guarantees, gaps, and hardening recommendations across each system boundary.

---

## 1. Publisher to Receiver

The receiver accepts incoming webhook requests and persists them directly into PostgreSQL before returning an HTTP 202/200 response.

- **Guarantees**:
  - Enforces idempotent ingestion using a unique constraint on `(account_id, idempotency_key)`.
  - Scoping the unique key by `account_id` provides multi-tenant namespace isolation, ensuring that keys generated by one tenant cannot collide with or block another tenant.
  - Repeated ingestion requests return the existing record instead of creating duplicate events.

---

## 2. PostgreSQL to Dispatcher

The dispatcher periodically scans for eligible events (`pending` and due `retriable`) and claims them for publishing.

- **Guarantees**:
  - Multiple concurrent dispatchers safely coordinate via PostgreSQL `FOR UPDATE SKIP LOCKED` and lease assignments (`lease_owner`, `lease_expires_at`).
  - If a dispatcher crashes after claiming an event, its lease naturally expires, returning the event to the pool for another dispatcher to claim.

---

## 3. Dispatcher to RabbitMQ

The dispatcher publishes claimed events to RabbitMQ and marks their database status as `published`.

- **Guarantees**:
  - Events are published as persistent messages to a durable queue before dispatch completion.
- **Consistency Gaps & Edge Cases**:
  - **Dual-write partial failure**: If the dispatcher crashes after publishing to RabbitMQ but before updating PostgreSQL to `published`, the lease will expire and the event will be re-dispatched, producing a duplicate queue message.
  - **Broker persistence**: Standard publishes without publisher confirmations cannot guarantee broker persistence during immediate broker restarts.
- **Hardening Recommendations**:
  - Use a **Transactional Outbox pattern** (writing queue payload to an outbox table in the same DB transaction).
  - Enable **RabbitMQ Publisher Confirms** to guarantee acknowledgment from the broker before updating state.
  - Add a periodic reconciliation job to clean up unconfirmed or expired leases.

---

## 4. RabbitMQ to Worker & Partner

Workers pull events from RabbitMQ, make HTTP POST requests to partner endpoints, record the outcome in PostgreSQL, and manually acknowledge the queue message.

- **Guarantees**:
  - Manual RabbitMQ acknowledgments ensure a message is only acked after the delivery outcome and attempt record are committed in a local PostgreSQL transaction.
  - On retryable failures (network error, `429`, `5xx`), the worker updates the status to `retriable` with an exponential backoff `next_retry_at` timestamp.
- **Consistency Gaps & Edge Cases**:
  - **Worker crash before ACK**: If the worker crashes after calling the partner or committing to PostgreSQL but before sending the RabbitMQ ACK, RabbitMQ will redeliver the message.
  - **Missing partner deduplication headers**: Currently, the worker forwards the raw payload without injecting a stable event or delivery ID header (e.g., `X-Delivery-ID` / `X-Event-ID`), making partner deduplication dependent on identifiers embedded inside the caller's payload.
  - **No duplicate suppression on redelivery**: A redelivered message for an event already in `delivered` state is not preemptively suppressed by the worker before making the HTTP call.
- **Hardening Recommendations**:
  - Inject standardized delivery and event headers (`X-Event-ID`, `X-Delivery-Attempt`) into outgoing partner requests.
  - Check database event status prior to executing the HTTP call to suppress redundant deliveries.

---

## 5. Terminal Failure and Dead-Letter Queue (DLQ)

When an event encounters a non-retryable error (e.g., permanent `4xx`) or exhausts its `max_attempts`, it transitions to `dead_letter`.

- **Guarantees**:
  - The worker records the terminal failure outcome, status code, and reason in PostgreSQL, then publishes an event notification to the RabbitMQ DLQ for operator visibility.
- **Consistency Gaps & Edge Cases**:
  - **Crash between DB write and DLQ publish**: A failure after marking the database row as `dead_letter` but before publishing to the DLQ leaves a terminal record in PostgreSQL without an alert in the DLQ.
  - **DLQ publish failure causes redelivery**: If publishing to the DLQ fails, the message is unacknowledged and will be retried, which may produce duplicate DLQ notifications.
- **Hardening Recommendations**:
  - Emit dead-letter notifications through an outbox table to guarantee atomicity with database state transitions.
  - Implement an idempotent DLQ consumer keyed by event ID.
  - Run a reconciliation check to identify dead-letter events in the DB that lack a corresponding DLQ dispatch.

---

## 6. System Invariants

1. **At-Least-Once Delivery**: No step guarantees exactly-once delivery; partner endpoints must handle duplicate HTTP POST requests.
2. **Authoritative State in PostgreSQL**: PostgreSQL is the single source of truth for event lifecycle, attempt history, and retry scheduling. RabbitMQ is a transient delivery buffer.
3. **Idempotent Ingestion**: Acceptance by the receiver guarantees a durable, deduplicated event record under `(account_id, idempotency_key)`.
4. **Safe Failure Recovery**: System crashes at any stage default to retrying or reclaiming work rather than dropping events.
